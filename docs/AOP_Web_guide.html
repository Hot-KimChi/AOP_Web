AOP Web 사용자 안내서

데이터 조회부터 검증 리포트까지

Flask 백엔드, Next.js 웹 화면, MS-SQL Server를 연결해 측정 데이터 생성·조회·검증·문서화를 지원하는 업무용 애플리케이션입니다.

빠른 이동 프로젝트 개요 기능 안내 기본 사용 흐름 기능별 상세 흐름 데이터 workflow 실행 방법 로그인·보안 문제 해결

프로젝트 개요

AOP Web은 사용자가 브라우저에서 데이터베이스와 분석 기능을 안전하게 사용하도록 화면과 API를 분리한 풀스택 애플리케이션입니다.

구성역할
Next.js 15 / React 18메뉴, 입력 화면, 데이터 표, 결과 다운로드를 제공합니다.
Flask / Python인증, 데이터베이스 조회, 파일 처리, ML 및 리포트 API를 실행합니다.
MS-SQL Server업무 데이터와 측정·검증 대상 테이블을 저장합니다.
인증은 Windows 도메인 계정의 Kerberos SSO를 사용합니다. NTLM은 허용되지 않으며, 서버 SPN과 브라우저 인트라넷 신뢰 설정이 필요합니다.

공통 데이터 화면

생성·조회 결과는 데이터 화면에서 공통으로 다룹니다. 열별 연쇄 필터, 정렬, 셀 편집, 행 삭제, 되돌리기, 저장, CSV 다운로드를 지원하며 편집 데이터의 행 정체성을 유지합니다.

기본 사용 흐름

  1. 애플리케이션 접속: HTTPS로 접속하고, Kerberos SPN에 등록된 DNS 호스트명을 사용합니다. 예: https://SPN-등록-호스트명:3000
  2. 로그인: 로그인 창에서 Windows 계정으로 SSO를 수행합니다. 허용 목록(AUTH_ALLOWED_USERS)에 등록된 도메인 계정만 사용할 수 있습니다.
  3. 기능 선택: 상단 메뉴에서 조회, MeasSet 생성, 검증, SSR 문서 출력, ML 중 필요한 기능을 엽니다.
  4. 조건 입력 및 실행: DB·테이블·프로브·파일 등 필수 조건을 순서대로 선택하고 실행 버튼을 누릅니다.
  5. 결과 확인: 표의 필터·정렬로 결과를 좁히고, 필요한 경우 편집 후 저장하거나 CSV·Word 파일로 다운로드합니다.
  6. 로그아웃: 작업이 끝나면 메뉴의 로그아웃을 사용합니다. 발급된 토큰은 폐기되어 다시 사용할 수 없습니다.

기능별 상세 흐름

각 기능은 로그인된 사용자의 브라우저에서 입력값을 확인한 뒤 인증 쿠키를 포함한 Flask API를 호출합니다. 처리 결과는 화면에 표시되며, 필요한 경우 파일로 저장하거나 다음 기능의 입력으로 이어집니다.

1. 홈 · 일정과 내 할 일

업무 시작 전에 일정과 개인 작업을 확인하는 진입 화면입니다.

입력로그인 상태, 새 할 일 제목
처리로그인 상태를 확인하고 계정별 할 일 목록을 불러옵니다. 할 일 추가·완료·삭제는 현재 계정 소유 데이터에만 적용됩니다.
결과SharePoint 주간 일정과 내 할 일 패널이 표시됩니다.
사용 순서로그인 → 일정 확인 → 제목 입력 후 추가 → 완료한 항목 체크 → 필요 없는 항목 삭제

2. MeasSet Generation · 측정 설정 CSV 생성

DB 기준 정보와 업로드 파일을 조합해 측정 설정 데이터를 생성하는 흐름입니다.

입력대상 데이터베이스, 프로브, 생성에 필요한 파일
처리DB·프로브 목록을 조회하고 파일을 서버에 전달해 MeasSet 생성 API를 실행합니다. 생성된 CSV 키로 결과를 다시 조회합니다.
결과생성된 CSV가 표로 표시되고 서버의 1_uploads\0_MeasSetGen_files\ 아래에 저장됩니다.
사용 순서DB 선택 → 프로브 선택 → 파일 선택 → Generate 실행 → CSV 검토 → 새 창에서 편집·다운로드 → 필요 시 SQL 반영
생성 결과를 SQL에 반영하기 전에는 열 값과 행 수를 확인하세요. 표에서 수정한 값은 저장·반영 동작을 실행해야 서버 데이터에 적용됩니다.

3. Viewer · 데이터 조회와 편집

허용된 데이터베이스와 테이블의 현재 데이터를 확인하고 필요한 범위만 다루는 기능입니다.

입력데이터베이스, 테이블
처리서버가 허용 목록을 확인한 후 테이블 데이터를 조회합니다. 데이터 화면은 열별 필터·정렬을 적용하며 현재 열을 제외한 조건으로 옵션을 계산합니다.
결과행·열 데이터가 표시됩니다. 편집본은 행 정체성을 유지하면서 저장하거나 CSV로 내보낼 수 있습니다.
사용 순서DB 선택 → 테이블 선택 → 데이터 보기 → 필터·정렬 → 셀 수정 또는 행 삭제 → 저장/되돌리기/CSV 다운로드

4. Verification Report · Tx 검증 리포트

Tx 요약 파일과 DB의 기준 데이터를 조건별로 대조해 검증 결과를 만드는 흐름입니다.

입력검증 DB, 프로브, Imaging SW 버전, Tx 요약 파일
처리선택 조건에 맞는 DB 데이터를 조회하고 파일 형식·필수 열을 검증한 뒤 Tx 비교 API를 실행합니다.
결과매칭·비교 결과가 화면에 표시되고 검증 리포트가 1_uploads\1_Verification_Reports\ 아래에 저장됩니다.
사용 순서DB 선택 → 프로브·SW 버전 선택 → Tx 파일 업로드 → 파일 미리보기/검증 → 비교 실행 → 결과 확인 및 리포트 다운로드
파일 선택 후 조건을 바꾸면 이전 미리보기와 매칭 결과가 현재 조건과 일치하는지 다시 확인하세요.

5. SSR DocOut · Word 문서 출력

SSR 데이터를 문서 형식으로 정리해 공유하거나 보관하는 기능입니다.

입력데이터베이스, SSR 데이터, 하나 이상의 Meas SS ID
처리선택한 DB의 SSR 테이블에서 대상 행을 조회하고 서버가 Word 문서를 생성합니다.
결과브라우저에서 Word 파일 다운로드가 시작됩니다.
사용 순서DB 선택 → SSR 데이터 로드 → 행 클릭으로 ID 선택 → 선택 항목 검토 → Word 출력

6. Machine Learning · 모델 학습과 평가

등록 모델의 버전과 성능을 확인하고 학습·예측 결과를 비교하는 기능입니다.

입력모델·학습 조건·필요한 데이터 선택
처리모델 목록과 버전 성능을 조회하고 학습 요청을 서버에 전달합니다. 학습 완료 후 성능 및 예측 지점 데이터를 다시 조회합니다.
결과모델 버전별 성능과 예측 산점도가 차트로 표시됩니다.
사용 순서모델 확인 → 학습 조건 입력 → 학습 실행 → 새 버전 확인 → 성능·예측 차트 비교 → 필요 시 버전 정리
학습은 데이터 양과 서버 상태에 따라 시간이 걸릴 수 있습니다. 실행 중에는 중복 학습 버튼을 누르지 말고 완료 상태를 확인하세요.

공통 결과 처리 흐름

  1. 검토: 결과 건수, 필수 열, 오류 메시지를 먼저 확인합니다.
  2. 범위 축소: 필터와 정렬을 사용해 필요한 행만 찾습니다. 필터는 표시만 바꾸며 원본 DB를 즉시 변경하지 않습니다.
  3. 수정: 편집 가능한 화면에서 셀을 바꾸거나 행을 삭제합니다. 실수하면 되돌리기를 사용합니다.
  4. 확정: 저장·SQL 반영·파일 출력처럼 명시된 확정 동작을 실행합니다.
  5. 보관: CSV·Word·검증 리포트를 다운로드하고 업무 규칙에 따라 별도 보관합니다.

데이터 workflow

각 기능은 입력 데이터를 정규화하고, 기준 키로 매칭한 뒤, 계산·비교 결과를 출력합니다. 아래 흐름은 “무엇을 넣으면 어떤 기준으로 연결되고 무엇이 나오는가”를 한눈에 보여 줍니다.

MeasSet 생성

입력 파일 + database + probeId + probeName

파일 로드 → 중복 제거·그룹 인덱스 생성 → 파라미터 시퀀스 생성 → intensity/power/temperature 예측 → 세 결과를 합쳐 CSV 저장

출력: 1_uploads\0_MeasSetGen_files\의 생성 CSV

Tx 검증 매칭

Tx 파일 + ProbeID + Software_version

파일 컬럼을 DB 스키마에 매핑 → ProbeID·SW로 파일과 DB를 필터링 → Mode별 행 연결 → 파라미터별 DB 값과 파일 값 비교

출력: DBValue / FileValue / Match / Status 비교 행

Tx 비교 리포트

probeId + TxSumSoftware + wcsSoftware + Meas SS ID

필수 키를 확인한 뒤 SQL Server의 TxCompare 프로시저에 전달하고 결과 행을 리포트 데이터로 반환

출력: 프로시저 결과 행·열과 비교 메시지

ML 평가

model + model version

모델·버전·메트릭을 model_id/version_id로 그룹화하고, 예측 포인트를 target_value와 estimation_value로 연결

출력: 버전별 성능 메트릭·예측 산점도 데이터

Tx 파일과 DB가 매칭되는 순서

  1. 기준 선택: 사용자가 선택한 ProbeID와 Software_version으로 DB의 Tx_summary 행을 조회합니다.
  2. 컬럼 정규화: 파일의 열 이름을 소문자·영숫자 키로 바꿔 Probe_ID와 ProbeID처럼 표기가 다른 열도 DB 스키마와 연결합니다.
  3. 파일 필터링: 파일에 ProbeID와 Software_version이 있으면 선택값과 정확히 일치하는 행을 우선 사용합니다. 일치 행이 없으면 비교 화면을 비우지 않고 파일 전체를 표시합니다.
  4. Mode 연결: DB와 파일을 각각 Mode별로 묶습니다. 같은 Mode의 파일 행은 모두 유지하며, DB에만 있으면 DB_ONLY, 양쪽에 있으면 BOTH, 파일에만 있으면 FILE_ONLY가 됩니다.
  5. 파라미터 매핑: 각 Mode의 파라미터를 순서대로 읽어 DB 값과 파일 값을 나란히 만들고, 파일 값이 존재하면 Match=O, 컬럼이 없거나 비어 있으면 Match=X로 표시합니다. 이 표식은 값의 동등성 판정이 아니라 파일 값의 매핑 가능 여부를 뜻합니다.
매칭 예시: 파일의 Probe_ID는 DB의 ProbeID로, Mode=M1은 DB의 같은 Mode 행으로 연결됩니다. 파일에 TxPulseRle 열이 없으면 해당 파라미터는 UNMATCHED로 표시됩니다.

Workflow A · Viewer 조회 → 필터 → CSV 출력

  1. 상단 메뉴에서 Viewer를 선택합니다.
  2. 데이터베이스 목록에서 업무 대상 DB를 선택하고, 테이블 목록에서 확인할 테이블을 선택합니다.
  3. 데이터 보기를 눌러 표가 나타나는지 확인합니다.
  4. 열 제목의 필터에서 원하는 값만 선택하고, 숫자 열은 정렬해 범위를 확인합니다.
  5. 필요한 행만 남았는지 확인한 뒤 CSV 다운로드를 누릅니다.
입력→출력 예시: DB/테이블 선택 → Probe=A, Version=3.2 필터 → 전체 2,400행 중 18행을 화면 데이터로 확정 → 측정_데이터.csv 출력.

필터는 화면에 보이는 행만 줄입니다. 원본 DB를 수정하려는 목적이라면 셀 수정 후 별도의 저장 동작까지 확인해야 합니다.

Workflow B · 입력 파일 → MeasSet 생성 → CSV 출력

  1. MeasSet Generation에서 DB를 선택합니다.
  2. 목록이 갱신되면 대상 프로브를 선택하고, 담당자가 전달한 입력 파일을 파일 선택 상자에 넣습니다.
  3. Generate & View CSV를 눌러 처리 결과를 기다립니다.
  4. 새 데이터 화면에서 열 이름과 행 수를 확인하고, 잘못된 값이 있으면 셀을 수정합니다.
  5. 수정이 맞는지 다시 확인한 뒤 CSV를 다운로드합니다. SQL 반영 버튼이 있는 경우에는 업무 승인 후 실행합니다.
입력→출력 예시: 입력 파일과 프로브 조건 → 중복 제거·파라미터 생성·3종 예측 → XP_Value_1 검토 → 생성 CSV 출력.

처리 중 같은 버튼을 반복해서 누르지 마세요. 파일 확장자와 필수 열이 맞지 않으면 먼저 입력 파일을 수정해야 합니다.

Workflow C · Tx 파일 + DB 기준 → 파라미터 비교

  1. Verification Report에서 DB, 프로브, Imaging SW 버전을 차례로 선택합니다.
  2. Tx 요약 파일을 업로드하고 미리보기에서 파일명이 맞는지 확인합니다.
  3. 파일 검증을 눌러 필수 열과 형식 오류가 없는지 확인합니다.
  4. 오류가 없을 때만 비교 실행을 누릅니다. 오류가 있으면 안내된 열이나 값을 고친 뒤 다시 업로드합니다.
  5. 매칭 결과와 비교 결과를 확인하고 리포트를 다운로드합니다.
입력→출력 예시: ProbeID/SW 선택 + Tx 파일 → 컬럼·Mode 매핑 → DBValue와 FileValue 나란히 표시 → 파일 값 매핑 가능 O/없음 X 결과.

DB·프로브·버전 선택을 바꾼 뒤에는 이전 파일 결과가 현재 조건과 맞는지 다시 확인하세요.

Workflow D · SSR 행의 Meas SS ID → Word 출력

  1. SSR DocOut에서 데이터베이스를 선택하고 SSR 데이터를 불러옵니다.
  2. 문서에 넣을 행을 클릭해 선택합니다. 여러 행을 선택할 수 있습니다.
  3. 선택된 행 수와 Meas SS ID를 확인한 뒤 Word 출력을 누릅니다.
  4. 브라우저 다운로드 목록에서 Word 파일이 내려왔는지 확인합니다.
입력→출력 예시: SSR 테이블의 3개 행 선택 → 각 행의 measSSId를 ID 목록으로 전달 → 선택 행만 포함된 SSR_table.docx 출력.

Workflow E · 모델 버전 + 메트릭 → 예측 비교

  1. Machine Learning에서 등록된 모델과 기존 버전을 먼저 확인합니다.
  2. 학습 조건을 입력하고 학습 실행을 한 번만 누릅니다.
  3. 완료 후 새 버전이 목록에 나타나는지 확인합니다.
  4. 성능 차트와 예측 산점도를 기존 버전과 비교합니다.
입력→출력 예시: 모델 선택 → v12/v13의 version_id별 메트릭 그룹화 → target_value와 estimation_value 연결 → 오차가 낮은 버전 확인.

학습 중 브라우저를 새로 고치거나 중복 실행하면 안 됩니다. 완료 표시와 새 버전 생성 여부를 먼저 확인하세요.

실행 방법

Windows 서버에서는 프로젝트 루트의 통합 스크립트를 사용하는 것이 가장 간단합니다.

AOP_Web.bat start      개발 모드 시작
AOP_Web.bat prod       운영 모드 빌드 후 시작
AOP_Web.bat status     백엔드·프론트엔드 상태 확인
AOP_Web.bat restart    재시작
AOP_Web.bat stop       종료
AOP_Web.bat uninstall  Windows 자동 시작 작업 해제

처음 실행하는 경우 백엔드 가상환경과 프론트엔드 의존성을 먼저 준비합니다.

cd backend
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

cd ..\frontend
npm install
운영 모드 주의: AUTH_SECRET_KEY, FLASK_SECRET_KEY, ALLOWED_ORIGINS를 사용자 또는 시스템 환경변수에 영구 등록해야 자동 시작 이후에도 정상 부팅됩니다.

로그인·보안 동작

  • Express Custom Server가 Windows SSPI로 Kerberos 인증을 수행하고, Flask는 Node 서버의 공유 비밀과 AUTH_ALLOWED_USERS를 확인한 뒤 HttpOnly JWT 쿠키를 발급합니다.
  • NTLM 또는 인증 방식이 확인되지 않은 요청은 거부됩니다. 운영 환경은 도메인·SPN·정식 호스트명과 HTTPS를 구성해야 합니다.
  • 인증된 API 호출은 쿠키를 포함해 전송되며 서버는 허용된 DB·테이블 목록과 사용자 허용 상태를 확인합니다. 로그아웃된 토큰은 다시 사용할 수 없습니다.
  • 활성 로그인 세션은 단일 Flask 프로세스의 메모리에 보관합니다. 프로세스 재시작 시 기존 토큰은 무효화됩니다. 여러 worker/서버로 확장하려면 공유 세션 저장소가 먼저 필요합니다.
  • SQL Server는 브라우저 사용자의 SQL 비밀번호가 아니라 Flask 백엔드 프로세스 계정의 Windows 통합 인증으로 접속합니다. 해당 서비스 계정에 필요한 DB 권한을 부여해야 합니다.
  • 프론트엔드와 백엔드 요청은 같은 호스트명을 사용해야 인증 쿠키가 공유됩니다. HTTPS 운영에서는 COOKIE_SECURE=true와 구체적인 허용 Origin을 설정합니다.
  • 기존 개인 할 일은 과거 SQL 로그인명을 소유자로 사용하므로, Windows 도메인 계정으로 자동 이전되지 않습니다. 필요하면 backend\data\user_data.db를 백업한 뒤 관리자에게 계정 소유자 이전을 요청합니다.

문제 해결

증상확인할 내용
Windows 로그인 실패 또는 HTTP 503Node와 Flask가 같은 AUTH_SSO_SHARED_SECRET을 사용하는지, AUTH_ALLOWED_USERS에 계정이 있는지 확인합니다. NTLM은 허용되지 않으므로 도메인·SPN·호스트명·브라우저 인트라넷 신뢰 설정을 점검합니다.
401 또는 로그인 만료JWT 만료·로그아웃·Flask 재시작 여부를 확인하고 Windows SSO로 다시 로그인합니다.
데이터베이스 목록이 비어 있거나 조회 실패Flask 프로세스 계정의 SQL 권한, backend\AOP_config.cfg, ODBC Driver 17 설치 여부를 확인합니다.
운영 모드가 시작되지 않음운영 필수 환경변수와 logs\의 시작 로그를 확인합니다.
파일 생성·다운로드 실패입력 파일 형식과 필수 선택값을 확인하고, 저장소 루트의 1_uploads\ 쓰기 권한을 점검합니다.

상태 확인으로 원인을 좁히기 어려우면 scripts\AOP_Web.ps1 -Diagnose를 실행한 뒤 최신 로그를 함께 확인합니다.
